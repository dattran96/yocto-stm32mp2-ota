## 20a Lint and parse check

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every push and pull request, on
GitHub's `ubuntu-24.04` runners, with `permissions: contents: read`. No keys and no passwords are
available there, and none are needed:

| Job | What | Time (first run) |
|---|---|---|
| `lint` | `oelint-adv` 9.11.2: a report of all findings, then a gate that fails on errors | 11 s |
| `parse` | kas 5.5, `kas-container shell kas/stm32mp25-disco.yml -c "bitbake -p"` | 3 min |

- [`scripts/lint.sh`](../scripts/lint.sh) runs the same checks locally: `scripts/lint.sh` (gate)
  or `scripts/lint.sh --report`. The rules it switches off are listed there with the reason. Most
  are false alarms: the linter does not know ST's and meta-oe's variables and overrides
  (`stm32mpcommon`, `FLASHLAYOUT_*`, `VERITY_*`).
- One switched-off rule is a real finding, `oelint.vars.noncoreoverride`: the bbappends change
  dropbear, U-Boot, RAUC and others for every distro, not only `mydistro`. That is also what
  `yocto-check-layer` checks; it is a plan item.
- The parse job uses only `kas/stm32mp25-disco.yml`, without `kas/signing.yml`: parsing needs no
  keys. `kas-container` runs BitBake in kas's container image, which has the host tools Yocto
  needs, so the workflow has no own package list.

Locally, the parse check is:
```
cd ~/Dokumente/yocto/kas-work
~/kas-venv/bin/kas shell ../meta-mylayer/kas/stm32mp25-disco.yml -c "bitbake -p"
```
**Expected:** `Parsing of 2555 .bb files complete ... 0 errors.` (This rewrites `local.conf`
without the signing settings; the next `kas build` with `kas/signing.yml` writes them again.)

Check a run:
```
GH_HOST=github.com gh run list -R dattran96/yocto-stm32mp2-ota -L 3
```
**Expected:** `completed success` for the last push; the badge at the top of the README is green.

## 20c Full build on a self-hosted runner

### Why my PC and not GitHub's runners
A full build is too big for GitHub's free runners:

| | GitHub's free runner | My PC |
|---|---|---|
| CPU / RAM | 4 cores / 16 GB | 22 cores / 62 GB |
| Free disk | ~14 GB (~30 GB after deleting pre-installed tools) | 36 GB + the 25 GB sstate cache |
| Max job time | 6 hours | no limit |
| Cache | empty every time (`actions/cache`: 10 GB per repo) | sstate is already there |

From zero, the image is about 6000 tasks; on 4 cores that is often longer than 6 hours, and it
needs 50+ GB of disk. With a warm sstate cache, an unchanged build takes minutes. So the small
jobs (lint, parse) stay on GitHub, and the full build runs on my PC.

How companies do it:

| Option | What | Used by |
|---|---|---|
| Own build servers (most common for Yocto) | strong machines (64+ cores, big NVMe) with a self-hosted runner | most embedded teams: the warm cache stays on the disk, builds run all day, signing keys (HSM) and test boards can be attached |
| Cloud machines started per job | big AWS/Azure machines, sstate on shared storage (S3, network disk) | bigger teams with many builds at once |
| GitHub's paid larger runners | rented e.g. 64 cores, pay per minute | less common for Yocto: empty cache unless a shared sstate server is added |

This setup is the first option at a small size: a laptop instead of a dedicated server.

### How it fits together
```
 push to main ──► GitHub ──"job for label yocto"──► runner service (user ghrunner)
                                                       │ kas-container (podman, rootless)
                                                       ▼
                                   container: kas 5.5 + BitBake, clean Debian host tools
                                     /downloads            ← /srv/yocto/downloads (read + write)
                                     /srv/yocto/sstate     ← shared sstate (read-only mount)
                                     /sstate               ← the runner's own sstate
```

| Part | What it does | Why |
|---|---|---|
| User `ghrunner` | runs the runner and the build | cannot open `/home/dat` (keys, SSH, files), no `sudo`, no `docker` group |
| Runner service | asks GitHub for jobs, runs the steps of [`build.yml`](../.github/workflows/build.yml) | label `yocto`, systemd service, starts with the PC |
| Rootless podman | the build runs in kas's container image | same host tools in every build, nothing from the PC leaks in |
| `/srv/yocto` | the shared downloads and sstate (moved out of my home) | `~/yocto-downloads` and `~/yocto-sstate` are links to it, so my own commands stay the same |
| `kas/ci.yml` | `SSTATE_MIRRORS` from the shared sstate | CI reuses my results but can never change the cache my signed builds use |

`kas` is installed for `ghrunner` (`pip install kas==5.5`) only for the `kas-container` script:
it starts podman with the right mounts. The kas and BitBake that build are inside the container
image, the same version.

### Safety
| Who can run code on the PC | |
|---|---|
| A pull request from a fork | no: `build.yml` has no `pull_request` trigger, and workflow runs from outside contributors wait for my approval (repository setting) |
| Someone pressing "Run workflow" | only people with write access (only me) |
| A push to `main` | yes, that is the point |
| Someone with my GitHub login | yes, as `ghrunner`: 2FA on the GitHub account is important |

What a job can still do: use the network, and leave a process running as `ghrunner` (the runner
is not thrown away after each job). To switch CI off:
`sudo systemctl stop actions.runner.dattran96-yocto-stm32mp2-ota.yocto-builder`.
Not done yet: pin the GitHub actions (`checkout`, `upload-artifact`) to a commit instead of `@v4`.

### Setup
1. GitHub: Settings → Actions → General → "Require approval for all external contributors".
2. The user and the shared caches (`/srv` and `/home` are on the same disk, so `mv` is instant):
   ```
   sudo useradd -m -s /bin/bash ghrunner
   sudo loginctl enable-linger ghrunner
   sudo mkdir -p /srv/yocto
   sudo mv ~/yocto-downloads /srv/yocto/downloads
   sudo mv ~/yocto-sstate /srv/yocto/sstate
   ln -s /srv/yocto/downloads ~/yocto-downloads
   ln -s /srv/yocto/sstate ~/yocto-sstate
   sudo setfacl -R -m u:ghrunner:rwX -m d:u:ghrunner:rwX -m d:u:dat:rwX /srv/yocto/downloads
   sudo setfacl -R -m u:ghrunner:rX -m d:u:ghrunner:rX /srv/yocto/sstate
   chmod 700 ~/yocto-keys
   ```
   - `enable-linger`: podman works for `ghrunner` without a login.
   - The access rules are for the user `ghrunner`, not a group: in a rootless container the
     user's extra groups are lost. `d:` sets the rule for new files too.
   - `ln -s TARGET LINKNAME` makes a link: the real files are in `/srv/yocto`.

   **Expected:** `sudo -u ghrunner ls /home/dat` → `Permission denied`;
   `sudo -u ghrunner ls /srv/yocto/sstate | head -3` → folder names;
   `sudo -iu ghrunner podman info | grep -i rootless` → `rootless: true`.
3. kas and the runner, as `ghrunner` (`sudo -iu ghrunner`):
   `python3 -m venv ~/kas-venv && ~/kas-venv/bin/pip install kas==5.5`, then the "Download" and
   "Configure" commands from Settings → Actions → Runners → New self-hosted runner (Linux x64).
   Answers: group Enter, name `yocto-builder`, labels `yocto`, work folder Enter. The token on
   that page is secret.
4. The service, as my user (`/home/ghrunner` is closed to me, so through `sudo bash -c`):
   ```
   sudo bash -c 'cd /home/ghrunner/actions-runner && ./svc.sh install ghrunner && ./svc.sh start'
   ```
   **Expected:** `Active: active (running)`; on the Runners page `yocto-builder` is **Idle** with
   the labels `self-hosted, Linux, X64, yocto`.

### First run: host contamination in `tiff-native`
The first build failed after 6 minutes in `optee-os-stm32mp` `do_compile`:
```
ImportError: libLerc.so.4: cannot open shared object file: No such file or directory
```
- My PC has `liblerc-dev` installed. My own builds run without a container, and libtiff's
  `configure` turns on LERC by itself when it finds the library. The tiff recipe has no
  `PACKAGECONFIG` to stop that. So `tiff-native` from my PC linked to the PC's `libLerc.so.4`.
- `-native` sstate is shared between build hosts (uninative). CI took that `tiff-native` from the
  shared cache, and in the clean container Pillow (used by OP-TEE for its fonts) could not load it.

```
 my build (no container)                      CI build (container)
 PC has liblerc-dev → tiff-native links it → sstate → reused → libLerc.so.4 missing → fail
```

Fix: [`recipes-multimedia/libtiff/tiff_%.bbappend`](../recipes-multimedia/libtiff/tiff_%25.bbappend)
with `EXTRA_OECONF:append = " --disable-lerc"`: `tiff-native` is the same wherever it is built.
The general fix is to build everything in the same container, my own builds too
(`kas-container build` instead of `kas build`).

The same log showed `fatal: detected dubious ownership in repository at '/downloads/git2/...'`:
the shared downloads belong to my user, so git in the container refused them. Fix:
[`.github/ci-gitconfig`](../.github/ci-gitconfig) (`safe.directory = /downloads/*`), mounted as
`/etc/gitconfig`.

Second run (with both fixes): **success** in 38 min. `Attempted 6180 tasks of which 5996 didn't
need to be rerun`: 184 tasks were built again (tiff, everything that uses it, and tasks the
runner's own hash-equivalence database did not match). Downloads: `flash-image` 83 MB (zipped),
`my-image-manifest`.

Third run, nothing changed: **1 min 18 s**, 8 tasks. That is the normal case for a push that
only changes docs.

## 20e Signing in CI

**Goal:** CI signs the RAUC bundle and checks the signature, but never sees my real keys.

| Key | Where | Signs | Who trusts it |
|---|---|---|---|
| Development key | `~/yocto-keys/rauc` (my user) | bundles from my own builds | my board (its keyring) |
| CI test key | `/home/ghrunner/ci-keys` (only `ghrunner`) | bundles from CI | only the check in CI |
| Release key (later) | offline, or a signing server | release bundles | shipped devices |

```
 CI build ──► my-bundle ──signed with CI test key──► rauc info --keyring=CI CA → "Verified"
                                                  └─► my board: refused (it trusts only my dev CA)
 release (later): take the tested bundle ──rauc resign with the release key──► devices
```
The board refusing CI bundles is correct: CI results are for testing. For a release, the tested
bundle is signed again (`rauc resign`) on a machine that holds the release key; CI never gets it.

### Make the CI key (once)
As `ghrunner`, without a password (`-nodes`), because CI cannot type one. On the PC:
```
sudo -iu ghrunner
```
Then:
```
bash -ec '
mkdir -p -m 700 ~/ci-keys && cd ~/ci-keys
openssl req -x509 -newkey rsa:4096 -nodes -keyout ca.key.pem -out ca.cert.pem -days 3650 -subj "/O=yocto-stm32mp2-ota CI/CN=CI test CA" 2>/dev/null
openssl req -newkey rsa:4096 -nodes -keyout ci.key.pem -out ci.csr.pem -subj "/O=yocto-stm32mp2-ota CI/CN=CI test signing" 2>/dev/null
openssl x509 -req -in ci.csr.pem -CA ca.cert.pem -CAkey ca.key.pem -CAcreateserial -out ci.cert.pem -days 3650 -extfile <(printf "basicConstraints=CA:FALSE\nkeyUsage=digitalSignature\n")
openssl verify -CAfile ca.cert.pem ci.cert.pem
rm ci.csr.pem ca.key.pem ca.cert.srl
chmod 600 ci.key.pem
ls -l
'
exit
```
- The first `openssl` makes the CA (the trust anchor), the second the signing key, the third lets
  the CA sign the key's certificate.
- The CA key is deleted at the end: nobody can make new trusted certificates. A new key needs a
  new CA.
- `bash -ec` stops at the first error, so a typo cannot reach the `rm`.

**Expected:** `ci.cert.pem: OK`, then three files: `ca.cert.pem`, `ci.cert.pem`, and `ci.key.pem`
with `-rw-------`.

### How CI uses it
- [`build.yml`](../.github/workflows/build.yml) mounts `~/ci-keys` read-only as `/ci-keys` into
  the container; [`kas/ci.yml`](../kas/ci.yml) sets `RAUC_KEY_FILE` and `RAUC_CERT_FILE` to it.
- The step "Check the bundle" runs `rauc info --keyring=/ci-keys/ca.cert.pem` on the bundle and
  fails unless both lines are there:

**Expected** (in the run summary):
```
Compatible:     'stm32mp257f-dk-mydistro'
Verified inline signature by 'O = yocto-stm32mp2-ota CI, CN = CI test signing'
```

### Bug found: a new key did not sign the bundle again
The check failed with `unable to get local issuer certificate`, although the key was new: the
bundle was still the one from the run before, signed with my development key.
```
meta-rauc:  do_bundle[file-checksums] += "${RAUC_CERT_FILE}:False ${RAUC_KEY_FILE}:False"
BitBake:    entries marked ":False" mean "file does not exist" and are left out
→ key and certificate are not part of the task checksum → new key, same checksum
→ do_bundle comes from sstate → old signature
```
This hits local builds too: after a key change, the board would get bundles with the old key.
Fix in [`my-bundle.bb`](../recipes-core/bundles/my-bundle.bb): add the certificate again with
`:True` (a new key always comes with a new certificate):
```
do_bundle[file-checksums] += "${@'${RAUC_CERT_FILE}:True' if d.getVar('RAUC_CERT_FILE') else ''}"
```
Check it in a build folder:
```
bitbake -S none my-bundle
bitbake-dumpsig -t my-bundle do_bundle | grep "checksums of files"
```
**Expected:** the certificate with its sha256, e.g.
`This task depends on the checksums of files: [('/.../development-1.cert.pem', '…')]`
(before the fix: `[]`).

## Errors you may see
- `git push`: `refusing to allow an OAuth App to create or update workflow ... without 'workflow'
  scope`. The `gh` login may push code but not workflow files. Fix:
  `gh auth refresh -h github.com -s workflow` (browser login as the repository owner).
- `Could not find any self-hosted runner group named "..."`: the runner name was typed at the
  first question (the runner group). Run `./config.sh` again and press Enter there.
- `cd: /home/ghrunner/actions-runner: Permission denied`: that home is closed to other users.
  Use `sudo bash -c 'cd /home/ghrunner/actions-runner && ...'`.
- `libLerc.so.4: cannot open shared object file` or `detected dubious ownership`: see "First run"
  above.
- `signature verification failed: Verify error: unsuitable certificate purpose`: the signing
  certificate has `extendedKeyUsage=codeSigning`. RAUC checks for S/MIME signing, so make the
  certificate without `extendedKeyUsage` (see 20e).
- `unable to get local issuer certificate` right after a key change: the bundle was not signed
  again (see "Bug found" in 20e).
